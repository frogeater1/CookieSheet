# 退款表导入

数据导入页分别提供订单表和退款表入口，两者均支持 `.xls` 和 `.xlsx`，无需安装 Excel。

## 卖家备注 QQ 与订单维护

- 新订单优先识别“卖家备注”中的 `qq:` / `qq：` 后连续数字，QQ 大小写不限，允许标记周围空格；不把手机号、订单号、QQ群或 QQ 邮箱当作 QQ。多个不同 QQ 标记会提示核对；没有有效标记则使用下单模板 QQ，再沿用手机号匹配规则。已有同编号订单仍保留原用户归属。
- 订单查询、用户查询均支持确认后删除单笔订单。`POST /api/orders/delete` 校验确认时的用户与批次，在同一事务中删除订单、重算相关批次赠品。退款记录独立保留，改正 QQ 后重导订单可以重新匹配。
- 删除沿用已保存的批次赠品选项；缺少时返回 `gift_choice_required`，客户端要求分别选择满赠与 Set赠，确认后将选项与删除一起保存。取消或计算失败不会删除订单，也不会保存未完成的选项。
- 用户查询点击补邮后只更新当前订单显示，不重置搜索、展开状态或返回全部用户；失败恢复原状态。

## 保存与关联

- `refunds` 是独立表，以退款编号为主键，以订单编号建立普通索引，没有订单外键。订单尚不存在时也能保存。
- 只保存退款表中“退款状态”为“退款成功”的记录（去掉首尾空格后精确匹配）。“退款完成”、处理中、取消、拒绝等其他状态都跳过，导入结果显示跳过条数。运费退款不计入商品数量。
- 顺序覆盖仅在同类表内进行：订单表按订单编号更新已存在订单的金额和批次；退款表按退款编号覆盖成功退款。以实际导入顺序为准，后导入的成功退款即使申请/完结时间更早或完结时间为空，也覆盖已保存的同编号记录，不累加第二次。请按导出先后顺序依次导入文件。
- 订单编号全局唯一，同一订单只保留一条记录。允许同编号普通订单出现在不同批次的订单表中，以最后成功导入的订单表文件名（不含扩展名）确定所属批次；不按批次名称大小排序，也不按下单时间判断。后导入时将原订单移到新批次，订单查询和已售出商品汇总同步归入新批次，不重复统计。补邮表和独立退款表不改变原订单批次。
- `/api/orders/import-with-gifts` 将用户、订单金额、批次、补邮、赠品选择及重算放在同一数据库事务中提交。数据库写入或赠品计算失败时整份请求回滚，批次和赠品不会部分变更。客户端使用独立副本解析，取消导入不会污染查询缓存。
- 订单重导更新 `tag`（最后导入批次）及金额相关信息：`price`（实付金额）、`receivableAmount`（应收金额）、`productRefundAmount`（商品已退款金额）、`orderRefundStatus`（订单表退款状态，用于金额标色）；补邮状态、原商品型号及件数、用户归属、电话和下单时间均保留，满赠和 Set赠按本次手动选择处理。补邮行也不改变本次重导订单的状态；单独导入补邮记录仍沿用原有处理规则。
- 待处理、取消等非成功退款直接跳过，不覆盖已有成功记录；之后导入成功状态时再新增。新文件没有包含的订单或退款继续保留，不因重新导入被删除。退款表不会改写订单表的数量或金额，订单表也不会覆盖退款记录。
- 同一个退款文件内的重复编号仍按申请/完结时间合并；同一退款编号对应不同订单或商品时拒绝导入并提示冲突。顺序覆盖需要更新服务端和客户端，不涉及数据库结构变更。
- 每次刷新及订单导入结束后重新关联，支持先退款、后订单。普通订单不再因“已关闭”或“退款完成”被忽略；已关闭的补邮记录仍跳过。
- 匹配使用订单编号、商品名称和型号。没有型号时使用商品名称。名称和型号仅去掉首尾空格，不模糊匹配。
- 补邮识别共用同一规则：商品名称为“补邮”，或商品型号为“非偏远地区补邮”（去掉首尾空格后精确匹配）。订单导入时按补邮处理，根据发货时间标记该用户之前的订单；这类退款不参与商品匹配、退款数量计算或标色，也不计入等待订单、未匹配商品和已售商品统计。成功的补邮退款记录仍独立保存；即使商品 ID 相同，也不会匹配到原订单中的补邮商品。仅名称为“补邮或者补差价”、但型号不符合上述条件的记录不会因此被当作补邮。
- 找不到订单或商品时保留退款原记录；导入结果显示待匹配记录数。退款数量是派生值，不改写原购买数量和原实付金额。

## 单价与数量

订单查询的金额始终显示订单表“实付金额”。仅凭订单表“退款状态”即可标色：`退款完成(全额退款)` 为红色，`退款完成(部分退款)` 为橙色，无退款或退款关闭保持正常颜色；也支持全角括号。悬停可查看应收金额、实付金额和原退款状态。此标色独立于退款表和商品退款件数推算，不用金额为零推断全退。升级需执行 `AddOrderAmountRefundStatus` 迁移；旧订单默认没有状态，重新导入同批次订单表后补全，备份恢复包含这两个新增字段。

按固定订单表头导入：读取原商品件数，不读取订单商品 ID 或“商品单价”，也不从订单实付金额推算单价。`RemoveOrderProductIdAndUnitPrice` 迁移删除订单表的 `productId`、`productUnitPrice` 两列，客户端和服务端实体同步删除。退款表自身的 `productId` 仍作为原始退款资料保留，但不参与匹配。旧 JSON 备份可以恢复其他数据，其中已废弃的订单字段会被忽略。

先导入订单表即可显示订单金额及退款状态颜色。之后导入退款表，刷新时按订单号、商品名称和型号补充各商品的退款内容，不改写订单金额、金额颜色、原购买件数或补邮状态。相同商品的多笔成功退款中，“商品实付金额”是重复的原始金额，必须一致且不累计；“买家退款金额”按不同退款编号累计。非成功记录和运费退款不参与商品件数计算。

退款件数 = 累计成功商品退款金额 × 原购买件数 ÷ 退款表原商品实付金额。例如购买 3 张、原商品实付 21 元、成功退款 14 元，即退 2 张、剩 1 张。同订单多个型号分别计算，已售出商品汇总随缓存刷新使用最新退款结果。

退款表原商品实付金额缺失、无法换算整件、原订单同一型号有多行等情况显示“数量待核对”，不强制四舍五入。不同成功退款的原金额不一致、超额退款显示“退款明细有误”。金额误差仅允许半分以内的十进制计算误差。按金额推算件数以整件退款为前提，无法据此确认补差价等退款对应的实际退货数量。

订单导入额外保存“商品已退款金额”到可空字段 `productRefundAmount`，重导时随其他金额字段更新，不影响补邮状态。升级需先更新后端，启动时执行 `AddOrderProductRefundAmount` 迁移，再更新客户端。旧记录不回填为零；可重新导入订单表补全，备份恢复包含此字段。

按订单编号去重成功退款编号后，比较订单表商品已退款金额与退款明细的商品退款合计（不含运费、补邮）。缺失或合计不足显示“待导入退款明细”；合计超出订单记录、存在无法匹配的商品退款显示“退款明细有误”。超出也可能由退款表比订单表新导致，提示需核对两表并导入一致的最新数据。旧订单缺少商品已退款金额时，使用应收减实付与包含运费的退款合计核对；已退款但缺少可用核对金额时，提示重新导入订单和退款表。

由于订单退款合计无法确定缺失的是哪个型号，“待导入退款明细”记录先按原件数计入展示数量，商品显示“数量（待导入退款明细）”，顶部显示“净售出 数量 件（待导入退款明细）”；其他订单已确认的退款照常扣减。此数量仅为明细补齐前的暂计数量，不将缺失退款当作已确认零退款，Set赠仍暂不生成。“数量待核对”继续表示件数推算不确定，存在此类记录时不展示数字总计。明细补齐后重新计算数量并移除括号提示。

“退款明细有误”按未退款容错：保留异常状态、原始退款金额和核对原因，但用于发货、销量及 Set赠计算的退款件数为 0，按原商品件数正常发货。整笔订单合计不一致或存在未匹配商品时，作用于该订单所有普通商品；仅某个商品原金额冲突或退款超额时，作用于该商品，其他有效退款照常扣减。商品行提示“退款明细有误，按未退款发货”，已售出商品显示数值，顶部注明容错记录数。无退款记录的赠品保留原统计，补邮始终排除。重新导入一致数据后自动恢复正常扣减，不修改数据库中的原始退款记录、订单金额或补邮状态。

## 显示

用户查询和订单查询使用同一套逐商品标记：

- 全部退款：型号及数量为红色，附“已退 5/5”。
- 部分退款：型号、数量及“已退 3/5，剩 2”均显示为橙色。
- 数量不明：橙色显示退款金额及“数量待核对”。悬停可查看原因或计算依据。

订单查询与用户查询中的订单信息过长时自动换行，行高随内容增加，不以省略号截断。保留完整内容提示和已补邮的半透明样式。悬浮提示中的商品型号及数量使用相同退款颜色，并保留计算依据。订单金额以订单表实付为准，原商品数量不改写；Set赠使用扣除已确认退款后的剩余件数。

## 手动选择与重算赠品

每次订单、补邮或成功退款导入，逐批分别询问是否计算满赠、是否计算 Set赠，不沿用之前的回答。重复批次以本次选择覆盖此前选择：选“是”重新计算，选“否”清除对应旧赠品。跨批次时原批次与新批次分别确认。由于 Set赠的型号清单来自整个批次，处理覆盖相关批次的所有用户。没有关联订单的退款暂不影响赠品，之后导入订单时再询问。

重算先移除相关订单的旧 `99满赠`、`Set赠`，再按用户和批次生成，反复导入不会累加赠品。满赠仍是该用户在批次内订单实付合计每满 99 元赠一件；退款表不再次扣减订单实付金额。Set赠沿用“集齐批次所有商品型号算一套”的定义，按各型号退款后剩余数量的最小值生成，赠品和补邮不参与套数计算。赠品放在该用户该批次下单时间最晚的普通订单中，同时间按订单号确定顺序。

选择计算 Set赠后，若退款明细缺失或退款数量无法确认，清除该用户该批次旧 Set赠并暂不生成，导入结果提示待核对数量；补齐一致明细后再次导入并选择计算，恢复正确数量。“退款明细有误”则按未退款保留原件数参与套数计算，不阻止生成。未选择 Set赠时不报告其待核对数量。满赠仅在选择计算时按订单表实付计算。

`AddBatchGiftChoices` 迁移新增 `giftChoices` 表，保存每批次最近一次手动选择，供退款软删除时维护同一规则；删除退款不会开启已禁用的赠品。历史批次没有选择记录时，软删除不擅自改动赠品，下一次导入再询问。手动备份、恢复和清空包含此表；旧备份恢复后不假定用户开启赠品。退款导入使用 `/api/refunds/import-with-gifts`，客户端提交本次逐批选择；缺少相关批次的选择会整份回滚。旧导入接口明确提示升级客户端，避免不弹窗直接计算。需同步更新服务端和客户端。

订单查询增加“退款状态”筛选，可与搜索、日期、标签及时间排序组合使用，重置恢复“全部状态”。“有退款”包括已匹配商品的全退、部分退款及数量待核对；“含全退商品”和“含部分退款商品”分别按商品状态筛选，同一订单可能同时符合两者。“无退款”表示没有已匹配商品的退款标记；尚未匹配的退款仍在“待匹配退款”页查看。补邮及非“退款成功”记录不影响此筛选。

左侧“待匹配退款”页逐条显示尚未唯一匹配到商品的退款，排除非“退款成功”及补邮记录。原因分为未找到原订单、未找到对应商品型号、匹配到多个商品。支持按订单号、退款编号、商品名称或型号搜索，默认按退款时间从新到旧排序。导入原订单后重新进入或刷新页面，已匹配记录会自动移出；仅退款数量待核对但已唯一匹配商品的记录不列入此页。

待匹配退款支持逐条勾选、全选当前搜索结果、取消选择和删除所选，并保留每行删除按钮。搜索或重置会清空选择，避免删除筛选之外的记录；确认框显示所选数量和涉及订单数。

退款删除改为软删除：`refunds.isDeleted` 标记按退款编号持久保存，不删除原订单或用户。单条和批量删除均不再物理移除退款；普通查询、商品退款计算和待匹配列表排除已删除记录。同编号成功退款再次导入直接跳过，即使金额、订单号或商品内容发生变化也不会恢复；导入结果单独显示跳过已删除记录数量。批量删除由一条 SQL 原子执行，重复删除安全，并发导入通过删除状态并发校验防止恢复已删除行。

备份包含已删除记录及其标记，恢复会回到备份时刻的完整状态；主动清空全部数据也清除删除标记。旧版备份没有该标记时按未删除读取。升级前已被物理删除的退款无法自动追溯其编号。先部署后端 `SoftDeleteRefunds` 迁移，再使用新客户端；旧客户端的单条删除接口也已改为软删除。

“已售出商品”位于“用户查询”下方，按批次分组，批次内以商品名称和型号汇总；不同批次不合并。列表显示批次、商品名称、型号和净售出件数，支持搜索和批次筛选。默认包含“99满赠”和“Set赠”，补邮始终排除。净售出扣除已确认成功退款，存在退款数量待核对记录时显示“待核对”。未匹配退款不扣减并在页面提示。

## 部署

“清空全部数据”位于“备份与恢复”页，用户查询页不再提供该入口。清空范围为当前服务器全部用户、所有批次订单、全部退款（含待匹配记录和软删除标记）及赠品计算选择，不受页面筛选影响；成功后同时清除客户端缓存。确认框默认选择取消。最后一份手动备份保留，清空不自动备份，也不删除备份文件。

先更新服务器，再使用新客户端。`AddIndependentRefunds` 迁移新增独立退款表及订单字段；服务启动沿用现有 `Database.Migrate()` 自动应用迁移。部署容器的构建上下文仍是 `CookieSheetServer/`，Dockerfile 已包含共享退款项目。

`KeepOnlySuccessfulRefunds` 迁移清理历史非“退款成功”记录，并增加数据库状态约束；客户端解析和服务端保存也分别过滤其他状态。执行迁移前保留备份，回退该迁移仅移除约束，不恢复已清理记录。

旧服务器没有 `/api/refunds` 时仍可查询订单，但退款导入会明确提示先升级服务器。

开发检查可通过进程环境变量 `COOKIESHEET_API_URL` 指定独立测试 API；未设置时使用项目原有服务器地址。

## 本机 PostgreSQL 临时测试环境

### 关闭订单排除

订单表中的“订单状态”为“已关闭”（去除首尾空白）时，商品订单直接跳过，不新增订单或用户；同文件重复订单编号以最后一行状态为准。退款状态不用于判断订单是否关闭。

重新导入时，库中对应的旧关闭商品订单直接删除，随即退出订单查询、实付合计和已售出商品统计。相关批次仍逐批手动确认是否计算赠品，并在同一事务内完成删除和赠品重算。关闭的补邮行只跳过，不撤销历史补邮标记。退款表独立保存，删除订单不会删除退款记录。

旧库没有保存订单状态，需要原订单表才能识别历史关闭订单；不能用金额为零或退款状态代替关闭状态。本次不新增数据库字段，需要同时升级客户端和服务端。新版客户端使用 `/api/orders/import-excluding-closed`，连接旧服务器会明确要求升级，避免关闭订单编号被静默忽略。

真实 PostgreSQL 17 位于独立 Docker 容器 `cookiesheet-refund-test-db`。数据库只监听 `127.0.0.1:55439`，库名 `cookiesheet_refund_test`，用户 `cookiesheet_test`。本地服务为 `http://127.0.0.1:51873`，正常启动时会执行真实数据库迁移。
