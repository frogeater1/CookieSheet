# 退款表导入

数据导入页分别提供订单表和退款表入口。退款仅支持 `.xlsx`，无需安装 Excel。旧版 `.xls` 请先另存为 `.xlsx`。

## 保存与关联

- `refunds` 是独立表，以退款编号为主键，以订单编号建立普通索引，没有订单外键。订单尚不存在时也能保存。
- 只保存退款表中“退款状态”为“退款成功”的记录（去掉首尾空格后精确匹配）。“退款完成”、处理中、取消、拒绝等其他状态都跳过，导入结果显示跳过条数。运费退款不计入商品数量。
- 同一退款编号重复导入更新该记录，不累加第二次。待处理记录直接跳过，之后导入成功状态时再新增；较旧的完结时间不会覆盖较新的记录。
- 每次刷新及订单导入结束后重新关联，支持先退款、后订单。普通订单不再因“已关闭”或“退款完成”被忽略；已关闭的补邮记录仍跳过。
- 匹配使用订单编号、商品 ID（双方都有时，否则使用商品名称）和型号。没有型号时使用商品名称。名称和型号仅去掉首尾空格，不模糊匹配。
- 商品名称为“补邮”的退款不参与商品匹配、退款数量计算或标色，也不计入等待订单和未匹配商品。成功的补邮退款记录仍独立保存；即使商品 ID 相同，也不会匹配到原订单中的补邮商品。
- 找不到订单或商品时保留退款原记录；导入结果显示待匹配记录数。退款数量是派生值，不改写原购买数量和原实付金额。

## 单价与数量

订单新增 `productUnitPrice` 和 `productId` 数组，与现有商品数组下标对应。商品单价列存在时直接保存；单商品订单且运费明确时，按 `(整单实付 - 运费) / 数量` 保存单价。多商品订单没有逐商品单价时不分摊整单金额。

关联后优先使用原订单已保存单价。旧数据缺少单价时，使用退款表的“商品实付金额 / 原订单对应商品数量”还原单价。相同商品的多笔退款中，“商品实付金额”是重复的原始金额，不累计。

累计成功退款金额除以单价得到退款数量。例如购买 5 张、商品实付 35 元、成功退款 21 元，即退 3 张。

单价缺失、金额不一致、超额退款、无法换算整件、原订单同一型号有多行等情况显示“数量待核对”，不强制四舍五入。金额误差仅允许半分以内的十进制计算误差。

## 显示

用户查询和订单查询使用同一套逐商品标记：

- 全部退款：型号及数量为红色，附“已退 5/5”。
- 部分退款：型号、数量及“已退 3/5，剩 2”均显示为橙色。
- 数量不明：橙色显示退款金额及“数量待核对”。悬停可查看原因或计算依据。

保持单行、省略号、完整内容提示，以及已补邮的半透明样式。悬浮提示中的商品型号及数量使用相同退款颜色，并保留计算依据。原订单金额、赠品计算和既有导出字段仍表示原订单数据，本功能没有将它们改成扣除退款后的统计。

订单查询增加“退款状态”筛选，可与搜索、日期、标签及时间排序组合使用，重置恢复“全部状态”。“有退款”包括已匹配商品的全退、部分退款及数量待核对；“含全退商品”和“含部分退款商品”分别按商品状态筛选，同一订单可能同时符合两者。“无退款”表示没有已匹配商品的退款标记；尚未匹配的退款仍在“待匹配退款”页查看。补邮及非“退款成功”记录不影响此筛选。

左侧“待匹配退款”页逐条显示尚未唯一匹配到商品的退款，排除非“退款成功”及补邮记录。原因分为未找到原订单、未找到对应商品型号、匹配到多个商品。支持按订单号、退款编号、商品名称或型号搜索，默认按退款时间从新到旧排序。导入原订单后重新进入或刷新页面，已匹配记录会自动移出；仅退款数量待核对但已唯一匹配商品的记录不列入此页。

## 部署

先更新服务器，再使用新客户端。`AddIndependentRefunds` 迁移新增独立退款表及订单字段；服务启动沿用现有 `Database.Migrate()` 自动应用迁移。部署容器的构建上下文仍是 `CookieSheetServer/`，Dockerfile 已包含共享退款项目。

`KeepOnlySuccessfulRefunds` 迁移清理历史非“退款成功”记录，并增加数据库状态约束；客户端解析和服务端保存也分别过滤其他状态。执行迁移前保留备份，回退该迁移仅移除约束，不恢复已清理记录。

旧服务器没有 `/api/refunds` 时仍可查询订单，但退款导入会明确提示先升级服务器。

开发检查可通过进程环境变量 `COOKIESHEET_API_URL` 指定独立测试 API；未设置时使用项目原有服务器地址。

## 本机 PostgreSQL 临时测试环境

真实 PostgreSQL 17 位于独立 Docker 容器 `cookiesheet-refund-test-db`。数据库只监听 `127.0.0.1:55439`，库名 `cookiesheet_refund_test`，用户 `cookiesheet_test`。本地服务为 `http://127.0.0.1:51873`，正常启动时会执行真实数据库迁移。

```powershell
# 启动临时库、本地 API 和连接临时环境的客户端
./scripts/Open-RefundTest.ps1

# 只启动临时库和本地 API
./scripts/Start-RefundTest.ps1

# 运行单元测试和真实 PostgreSQL/API 集成测试
./scripts/Test-RefundPostgres.ps1

# 停止临时环境，保留测试数据
./scripts/Stop-RefundTest.ps1
```

密码随机生成，和服务 PID 一起保存在已被 Git 忽略的 `.local/refund-test/environment.json`；不要提交该目录。服务发布到 `.local/refund-test/server/`，不会锁定正常编译目录。数据库数据保存在独立 Docker 卷中，重启后仍保留。

客户端通过当前进程的 `COOKIESHEET_API_URL` 连接临时 API，窗口标题显示“本地测试”。从测试启动脚本打开；直接双击原 EXE 仍使用原有默认服务器地址。

当前真实数据测试副本（2026-09-22）：

- 通过正式 API 的 GET 接口复制了 787 位用户和 2,114 笔订单，保留全部业务字段、用户编号及订单归属，并逐字段核对一致。正式服务未执行写操作。
- 原表 253 条退款中，仅保留 235 条“退款成功”记录，跳过其余 18 条。重复导入不增加记录。其中 20 条补邮退款不参与匹配；“待匹配退款”页显示 174 条记录，涉及 117 笔尚未存在的订单。已匹配商品中，36 项全部退款、4 项部分退款。
- 当前库不含 `TEST-` 模拟订单。复制前的临时库已备份至 `.local/refund-test/before-real-copy-20260922-161347.dump`。
- 清理非成功退款前的真实数据副本已备份至 `.local/refund-test/before-success-only-20260922-171732.dump`。

测试资料：

- `.local/refund-test/refund-sample.xlsx`：原 XLS 的转换副本，253 条退款，单元格值已逐一核对。
- `.local/refund-test/remote-users.json`、`remote-orders.json`：本次真实用户、订单副本，包含原有联系方式，仅保存在 Git 忽略目录中。
- `.local/refund-test/real-copy-result.json`、`real-refund-test-result.json`：本次复制和真实退款表导入的核对结果。
- `.local/refund-test/original-orders.json`、`test-result.json`：此前匿名化集成测试的输入和结果，包含先退款后订单、部分/全部退款、状态更新和非法批次回滚等检查。

`Test-RefundPostgres.ps1` 只允许固定的本机测试地址和库名，不会向正式服务写入。它会将原订单重新关联到测试用户，并新增 `TEST-` 演示订单，因此会改变当前真实数据副本。保留本次真实数据用于手动验收时，只运行启动脚本即可。
