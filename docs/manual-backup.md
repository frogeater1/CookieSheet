# 手动备份与恢复

客户端左侧“待匹配退款”下方的“备份与恢复”页面提供“备份全部数据”，保存当前服务器的一致性数据快照，包括全部用户、订单（含批次、商品数组、发货状态等）及全部成功退款记录（含待匹配退款）。不使用客户端缓存作为备份来源。

只保留最后一次成功的手动备份；没有定时任务，恢复也不会自动备份。空数据库也可以手动备份，会替换上一份备份。页面展示备份时间及各类记录条数。

“恢复最后备份”先显示备份时间和条数并要求确认，然后以事务整体替换当前三类业务数据。备份后的新增、修改和删除都会被撤销。校验或写入失败回滚；恢复不修改备份文件。确认期间如果有新备份生成，恢复会拒绝旧的确认，需重新确认。

## 部署

需要同时更新客户端和 CookieSheetServer，无需数据库迁移。备份不包含服务器配置、数据库账号或应用程序文件。

后端通过 `COOKIESHEET_BACKUP_DIR` 指定可写的持久目录；未指定时为服务器程序目录下的 `data-backups`，文件名 `latest.json`。文件含个人数据，应限制目录访问；不要提交到 Git。更新服务器时保留该目录。每个数据库应使用独立目录，当前实现用于单个服务器实例。

容器部署须把备份目录挂载为持久卷或主机目录，并授予运行用户写权限，例如将 `COOKIESHEET_BACKUP_DIR` 设为 `/app/data-backups`，挂载到该位置。仅保存在容器可写层的文件会随容器重建丢失。

已有 Compose 部署可在 `CookieSheetServer` 目录使用 `docker compose -f compose.yaml -f compose.backup.yaml up -d --build`，随附覆盖文件为备份挂载独立持久卷。不要删除该卷。

API：`GET /api/backups/latest`（无备份时 204）、`POST /api/backups`、`POST /api/backups/restore`（JSON：`backupId`）。接口沿用现有服务的访问方式，备份文件不会通过 API 下载。

## 验证

`DataBackupTests` 的普通测试检查缺失和损坏文件；PostgreSQL 测试需提供 `COOKIESHEET_BACKUP_TEST_ADMIN` 指向本机 55439 端口的测试数据库管理员连接。测试会创建随机命名的独立数据库，验证字段完整往返、失败回滚、最后备份替换、重复恢复、空备份、用户 ID 序列和备份写入失败保留原文件，最后删除自己的临时数据库。不会恢复现有业务数据库。
